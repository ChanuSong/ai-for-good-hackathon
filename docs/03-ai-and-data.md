# AI·데이터·출처 설계

상태: 로컬 규칙 기반 웹앱 구현, 모델 미연결 · 기준일: 2026-09-17

현재 앱은 [근거 데이터](../data/seocho-infertility.json)의 claim·출처를 사용한다. [JSON Schema](../data/roadmap.schema.json)와 [수용 사례](../data/acceptance-cases.json)는 초기 로드맵 데이터 설계·검사 자료다. 공개 원문 대조와 사람·기관 검증은 다르다. 현재 자료는 사람 검토 전이다. 현재 UI는 HTML/CSS/JavaScript이며 데이터베이스 없이 단일 세션 메모리만 사용한다. 모델·공개 호스팅은 미정이다.

현재 앱은 claim·용어·서류 구분 데이터를 사용한다. `data/document-preparation.json`과 `data/preparation-glossary.json`은 별도 자료이며 초기 로드맵 스키마의 대상이 아니다. 실제 동작의 기준은 [구현 계약](10-implementation-contract.md)이다.

아래 AI 생성·역할 배정·Household·Roadmap·Task 모델은 **후속 설계 이력**이다. 현재 UI에는 역할·Task 완료·profile_revision·요청 ID가 없으며 합성 조건과 언어·보기 상태만 메모리에서 관리한다.

## 1. 후속 AI 역할

| 역할 | 책임 | 제한 |
| --- | --- | --- |
| Intent Understanding | 자연어에서 지원 Life Event 식별 | 미지원 사건을 지원한다고 답하지 않는다. |
| Planning | 등록된 절차와 질문 ID의 선택을 보조 | 행정 요건·기한·기관·필수 순서는 기준 데이터에서 고정한다. |
| Personalization | 확인된 사용자 조건에 따라 분기 | 미확인 조건을 자격 충족으로 간주하지 않는다. |
| Role Assignment | 가족의 준비·확인 업무 담당자 제안 | 국적만으로 고정하지 않으며 법적 대리 권한을 판단하지 않는다. |
| Explanation | 복잡한 절차를 쉬운 언어로 설명 | 예외·조건을 설명에서 지우지 않는다. |
| Translation | 같은 정보의 한국어·일본어 표현 | 번역 과정에서 새로운 요건을 만들지 않는다. |

AI는 준비·안내·확인을 지원한다. 법률, 복잡한 체류자격 변경, 의료적 판단, 대출 승인, 조세, 지원금 최종 자격 판정은 자동 결론의 대상에서 제외한다.

## 2. 생성 흐름 제안

1. 사건을 분류하고 지원 범위를 확인한다.
2. 사건별 필수 프로필과 이미 제공된 정보를 대조한다.
3. 앱이 조건에 맞는 등록 자료를 선택한다. 조건 미확인은 별도 확인으로 남긴다.
4. AI 출력은 지원 사건·질문 ID 등 허용된 구조로 한정한다. 행정 핵심 문구·근거·순서는 앱이 기준 데이터에서 조립한다.
5. 앱이 스키마, 참조, 의존관계, 자료 버전, 근거 상태 보존을 검사한다. 출처 ID가 존재한다는 사실만으로 새 문장이 사실임을 인정하지 않는다.
6. 통과한 결과를 같은 Roadmap의 한국어·일본어로 표시한다. 팀 검토 전 상태도 유지한다.
7. 근거 부족·출처 충돌·미확인 조건은 확인 필요 상태로 남긴다.

첫 데모는 등록 자료를 사용하며 실시간 검색·대규모 RAG는 제외한다. 자연어 사건 이해 등 실제 연결한 AI 역할만 발표한다. 고정 자료로 동작하는 대안은 AI 생성으로 소개하지 않는다. 문서·입력 속 지시문, 임의 URL, 잘못된 근거 참조를 처리하는 기준은 [구현 계약](10-implementation-contract.md)에 있다.

## 3. 최소 데이터 모델

| 개체 | 주요 필드 | 목적 |
| --- | --- | --- |
| Profile | 고정 합성 가구, 지역·혼인·보험 확인·시술 시작 여부·언어, revision | 첫 데모의 최소 조건 |
| Household Member | 가구 내 ID, 표시 이름, 관계 | 역할의 기준 고정 |
| Roadmap | ID, 사건 코드, 제목·요약, 확인 필요 조건, Task 목록, 자료 모드 | 같은 사건의 진행 관리 |
| Task | ID, 제목·이유, 담당자·완료, 적용 확인 상태, claim 참조, 의존관계 | 준비 행동 단위; 상세는 claim을 통해 표시 |
| Claim | ID, 한일 문구, 출처·원문 위치, 근거 확인 상태, 사람 검토자 | 요건·방법·기관·서류·충돌을 주장별로 관리 |
| Source | ID, 공식 URL, 발행기관, 자료 제목, 적용 범위, 확인일, 변경일, 검증 상태 | 행정정보의 추적 가능성 |

첫 데모는 합성 조건만 처리한다. 실제 국적·체류자격·등록번호·여권번호·의료기록을 받지 않는다. 상태는 브라우저 메모리에만 두며 새로고침·탭 종료·초기화로 제거한다. 외부 AI에 자유 입력을 보내지 않는 기준과 호스팅 로그 점검은 [데이터 처리 계약](10-implementation-contract.md)에 따른다.

## 4. 현재 데이터 계약

[근거 데이터](../data/seocho-infertility.json)와 [JSON Schema](../data/roadmap.schema.json)를 함께 사용한다. 초기 `0.1-draft` 예시는 v1 계약으로 대체했다. 데이터셋은 공개 자료와 준비 Task를 담고, 초기 설계의 `profile_revision`·요청 ID는 현재 앱에서 구현하지 않았다. 현재 앱은 선택 언어·조건만 별도 관리한다.

- `sources`: 원문 URL·기관·확인일·사람 검토자.
- `claims`: 한일 문구·출처 ID·원문 위치·근거 확인 상태.
- `tasks`: 준비 행동·이유·claim ID·의존관계·담당자·완료·적용 상태.
- 준비물·기관·방법·주의사항은 연결된 claim으로 표시한다. 이 v1 데이터는 완전한 개인별 신청서류 목록이나 모든 채널의 이용 가능성을 보증하지 않는다.

스키마는 구조를, 데이터 검사기는 참조·의존관계·근거 상태 등 도메인 제약을 확인한다. 등록된 출처가 문장을 실제 뒷받침하는지와 번역의 의미는 사람이 추가 검토해야 한다.

## 5. 필드 규칙

| 필드 | 규칙 |
| --- | --- |
| `data_mode` | 이 데이터셋은 `official_sources`. 이것만으로 사람 검토나 개인 적용을 확정하지 않는다. |
| `review_status` | `human_review_pending` 또는 `human_reviewed`; 실제 검토 기록과 일치해야 한다. |
| `owner` | `user`, `spouse`, `together`; 기준 사용자를 고정하며 언어로 뒤집지 않는다. |
| `status` | `todo`, `doing`, `done`; 사용자 기록이며 기관 처리 결과를 증명하지 않는다. |
| `applicability` | `applicable`, `not_applicable`, `needs_confirmation`; 업무 적용 상태로, 최종 자격 승인과 다르다. |
| `deadline` | 이번 P0 데이터에서는 `null`만 허용. 확인 필요 기한을 화면에서 숨기지 않는다. |
| `depends_on` | 같은 데이터셋의 선행 Task ID; 순환·없는 참조 금지. |
| `claim_ids` | 등록 claim만 연결. 빈 근거로 행정 주장을 표시하지 않는다. |
| `evidence_status` | `source_checked`, `verified`, `needs_confirmation`, `conflicting`; 모델의 자신감과 무관하다. |
| `source_ids` / `locations` | claim별 실제 출처 ID와 대응하는 원문 위치. 무관한 홈페이지 링크로 대체하지 않는다. |
| `human_reviewer` | 실제 검토자 기록. 미실시는 `null`; 이름을 추측해서 넣지 않는다. |

`source_checked`는 Codex의 공개 원문 대조다. `verified`는 사람의 기록된 검토이며 **개별 사용자의 최종 자격 승인**을 의미하지 않는다. 모델은 검증 상태를 부여하거나 충돌을 해소할 수 없다. 검토자 없는 승격·임의 기한·등록되지 않은 claim을 거부한다. `applicability`, `status`, `evidence_status`는 독립적으로 관리한다.

## 6. 공식 자료 등록 양식

| 항목 | 작성 기준 |
| --- | --- |
| 자료 ID·제목 | 추적 가능한 고유 ID와 실제 문서 제목 |
| URL·발행기관 | 해당 주장으로 직접 연결되는 공식 안내 페이지 |
| 지원하는 정보 | 자격·서류·순서·기관·신청 경로 중 무엇의 근거인지 |
| 적용 범위 | 지역, 사업, 대상 조건, 유효 시기 |
| 확인일 | 담당자가 실제 본 날짜; 생성 시각으로 자동 대체하지 않는다. |
| 게시·수정일 | 원문에 있으면 기록하고 없으면 미상으로 둔다. |
| 외국인 관련 조건 | 원문에 명시된 내용과 추가 확인이 필요한 내용을 구분 |
| 검토자·확인 상태 | 팀 내 검토 담당자와 미확인·검증·충돌 상태 |

법령·정책 변경을 놓치지 않도록 행사 직전 실제 시연 자료를 재확인한다. 기존 URL의 존재만으로 내용의 최신성을 보장하지 않는다.

## 7. 다국어와 상태 일관성

- 사건·Task의 ID와 담당자·상태·근거는 언어와 분리해 관리한다.
- 한국어·일본어 표현은 같은 사실·조건을 참조한다. 언어 전환 때 Roadmap을 새로 생성하지 않는다.
- 기관명·서류명은 찾기 쉽도록 한국어 공식 명칭을 병기할 수 있다.
- 가족 화면이 별도 세션이면 역할을 가구 구성원 ID에 연결한다. `user`·`spouse`를 화면마다 무조건 뒤집지 않는다.
- P0는 새로고침 시 초기화한다. 기기 간 동기화·장기 저장은 제외한다. 프로필 변경 시 재생성과 완료 초기화 규칙은 구현 계약을 따른다.

## 8. 사용자에게 보여줄 불확실성

기본 문구:

> 이 조건은 사용자의 상황에 따라 달라질 수 있습니다. 담당기관 확인이 필요합니다.

일괄 경고로 끝내지 않고 **무엇을, 어디에, 어떻게 확인하면 되는지**를 해당 Task에 연결한다. 자료가 충돌하면 어떤 항목이 다른지 표시한다. 기관이 미확인이면 정확한 기관을 찾는 일을 다음 Task로 제시한다.

가족이 함께 보는 화면에는 업무 분담에 필요한 수준만 표시한다. 실제 의료 서류 업로드·공유는 P1의 별도 설계가 끝난 뒤 다룬다. 데모에서는 합성 프로필을 사용한다.
